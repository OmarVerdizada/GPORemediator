# Security boundary

Version 3.8.1 preserves the 3.6.0 security hardening and adds server-owned workflows. It is not a security certification or independent penetration-test report.

Workflow submission requires the same Windows roles, origin, JSON and identity-bound antiforgery controls as individual operations. Workflow reads and reports are restricted to the submitting operator. Delegated connection tokens stay in the bounded in-memory queue; durable records contain approvals and results only. Restart never replays a write. Batch steps recheck live fingerprints and values, reserve the GPO against local interleaved mutations, and stop remaining writes/refresh on an ambiguous result. Whole-batch restore requires separate approval and a validated final fingerprint. Reports encode untrusted fields and contain no executable scripts or external assets. JSON hashes detect alteration relative to their payload; they do not establish publisher authenticity. Read-only scans and endpoint samples must not be interpreted as a complete compliance or security assessment.

## Operator and execution identities

The service is local-only. Requests must originate from a loopback address and use a localhost/loopback Host header. Except for two minimal health endpoints, access requires the real Windows caller via Negotiate for session binding and audit context. The 2026-10-20 authentication update removes application roles, operator allowlists and role-specific endpoint/UI restrictions. Authenticated, signed-in users can manage configuration and read audit events. AD operations always run with the submitted domain credential; the DC enforces actual GPO and directory permissions. Production write gates, plan consent, CSRF/origin checks and backups remain required.

Version 3.8.1 uses one explicit startup sign-in in Windows/AD mode. The domain username and password establish the delegated connection through the existing read-only DC inventory operation; only after that succeeds is the startup confirmation issued. There is no second operator-password prompt. Negotiate identifies the local Windows operator for session binding and logging; it grants no application role. The operator and delegated execution identities remain distinct in audit records. Failed AD authentication or connection does not unlock the workspace. In initial Setup mode (before a domain is configured), Windows `LogonUserW` verifies the current Windows caller's password and SID for configuration access.

Passwords are not persisted or cached by the sign-in UI. The existing delegated server session holds only an encrypted credential in memory, subject to its 15-minute idle and two-hour absolute limits. One explicit sign-in endpoint issues both connection and startup cookies. Reconnect after expiry/disconnect uses that same screen; refresh does not prompt while the connection is valid. Five attempts per minute per operator and four concurrent AD connections limit retries; incorrect passwords can still trigger account lockout. Windows/AD requires a password-capable delegated account, and initial Setup requires a password-capable operator account.

Only a hash of a random 256-bit confirmation cookie is retained in server memory, bound to the authenticated Windows identity. The HttpOnly, SameSite=Strict cookie survives browser refresh/reopen; its client lifetime is capped at one year, but restarting the service invalidates it immediately because the proof table is not persisted. Confirmation does not expire during an ordinary running process. Signing in again rotates that actor's proof. At most 64 actor proofs are held. All API routes except the session bootstrap, confirmation endpoint and minimal health endpoints require the proof. Confirmation itself requires Windows authentication, same-origin JSON and antiforgery validation. Browser Negotiate may reuse Windows credentials, so the explicit domain sign-in is an application screen rather than a guaranteed native Windows Security dialog. Clearing browser cookies also requires confirmation again. Closing and reopening only the launcher/browser while the same backend remains running does not create a new server session.

The delegated AD execution account is separate from the browser identity. Its password is encrypted in server memory, passed to fixed worker scripts via stdin, and never placed in argv or persisted by the application. Sessions are bound to the operator, expire after 15 minutes idle or two hours total, and disappear on restart. Managed strings cannot be reliably erased; the launcher owner and local administrators remain trusted and can inspect process memory. Logins are limited to five attempts per minute per Windows identity, four concurrent connection attempts and 32 active sessions.

## Target planning access

All inventory objects readable by the execution account remain visible. Planning a remediation checks computed AD attribute-write access and native Windows SYSVOL modification access without write probes; any necessary link change requires effective gPLink write authority. Denied and unverifiable access are distinct errors with delegation guidance. An unchanged link is preserved rather than rewritten. Apply rechecks access, and Windows remains the authority for each operation. Read-only scans do not require edit delegation. See [access assessment and test limits](docs/TARGET-ACCESS-2026-10-20.md).

## Request and write protection

API mutations require the exact application Origin, application/json and an identity-bound antiforgery token. Cookies are HttpOnly and SameSite=Strict. The local HTTP deployment does not provide TLS confidentiality: never proxy or expose it to a LAN. Browser scripts use a self-only CSP; inline styles remain permitted for existing UI rendering. Request bodies are limited to 32 KiB.

Apply, rollback and refresh require the write gate and explicit authorized GPO/OU boundary. Refresh accepts only Pdc or Scope. Endpoint targets must be exact DNS names within the configured domain. Explicit host mode accepts at most 100 configured entries; automatic mode enumerates enabled computers only beneath the selected OU (including child OUs), with a 5,000-object bound. Existing host lists retain explicit mode until changed. Wildcard host execution is rejected. Effective endpoint verification samples at most five computers; a larger target list does not certify all endpoints. Existing backup, stale-plan, rollback-drift and interrupted-operation safeguards remain in force. A reported publication result does not establish effective endpoint compliance.

## Files and distribution

ProgramData configuration, state, data, backups and recovery use private DACLs for the launcher account, SYSTEM and local Administrators. Existing broad child permissions are replaced. Junctions and symbolic links are rejected. Failure to apply these protections stops startup. The installed runtime receives the same protection. Remote DC backup and manifest storage must separately be secured by the domain administrator; this release's local ACL checks do not validate remote storage permissions.

Data Protection keys are protected with current-user DPAPI. Legacy plaintext keys are retired to encrypted `.dpapi` recovery copies, intentionally invalidating old browser antiforgery tokens. Preserve the Windows account/profile and protected state when planning recovery.

The launcher checks archive SHA-256 and compares installed runtime content with the archive. The compiled backend serves its embedded UI and checks worker scripts against embedded hashes before execution. Checksums do not prove publisher identity if an attacker can replace the entire package. Authenticode signing and signed release provenance are still required for a stronger distribution chain. Do not run packages from an untrusted or shared writable directory; a local administrator or compromised launcher account can replace the product or alter its data.

Audit hashes detect inconsistent records; they are not externally anchored signatures and do not defend against a privileged attacker rewriting the full chain. Export audit records to an independently protected system when stronger evidence is required.

## Verification and remaining work

Automated tests cover role-free authenticated endpoints including casing/trailing slashes, origin/CSRF/identity isolation, login throttling, production refresh body mapping, host restrictions, script tampering, Windows ACL/junction rejection, DPAPI persistence/migration and embedded UI delivery. Workflow/mapping regressions and mocked browser recovery tests supplement these checks. GitHub CI runs these checks and a transitive NuGet vulnerability audit. A clean dependency result means no known advisory was returned at scan time; it is not proof of absence of vulnerabilities.

Before broad production use, perform an independent penetration test on an isolated domain lab: actual Windows/Negotiate authentication, privilege separation, concurrent/restarted operations, remote DC permissions, credential handling, GPO drift, rollback and endpoint refresh. Real AD execution was not performed for this release's automated local verification. Test runtime upgrades and recovery with the intended service account. Keep Windows, .NET release payloads and dependencies patched.

Report suspected vulnerabilities privately to the repository owner without publishing credentials, domain inventories or exploitable details in a public issue.
